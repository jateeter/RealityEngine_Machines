# Document assets and agentic maintenance update

The update changes the 225 native machine JSON candidates and their 225 agent specifications. It introduces explicit stewardship for 68 asset types, 1,459 machine-specific duties and 16 accountable families. Each duty states why the asset matters, who owns it, the machine’s contribution, what causes creation or revision, and what evidence/review makes the work complete.

## Behavior change

The former input-analyst objective primarily produced a normalized vector and described review duties. The new objective also seeks missing or stale accounting assets, requests authentic evidence, creates owned drafts, proposes revisions, reconciles dependencies, obtains independent review and invalidates outdated approvals. Correct evidence and visible unresolved work take priority over apparent document completion or a green compliance indicator.

The PE analyst binding remains advise-only and its completion parser/format is unchanged. A separate `documentWorkflowBinding` declares document operations, owned asset types and request-only cross-family types. Drafting agents cannot approve, forge issuer evidence, post journals, publish, file or release statements. The supplied reference library is a trusted internal executor; a production tool gateway must enforce those binding permissions and authenticate the name-string review decisions. This does not introduce an identity-management acceptance gate.

## Accounting content versus operational document choices

`required-statement` identifies the applicable statement set. `required-reporting-content` identifies required disclosures/reconciliations or information captured in an operational schedule. `supporting-control` and `engineering-control` identify our evidence workpapers/registers and software controls. The exact titles, containers and file formats are implementation choices; this bundle does not claim IFRS prescribes all 68 named documents. No legal retention period is invented. External contracts, valuations, signed decisions and authorisations are obtained/referenced, never generated as if issued by a third party.

## Native-machine integration

Each machine retains its IDs, sequences, input/output regions, match algorithm, assertion encoding, numerical bands and arbitration policy. `metadata.documentAssetWorkflow` carries the new objective, motivations, duties, triggers, completion requirements, ownership and orchestration boundary. The runbook description and document duty references are updated. Machine version is 1.4.0. Native engines can load these candidates under the existing extensible machine schema; they will not execute the new metadata by themselves.

The reference observation adapter validates the machine identity, known sequence, existing nominal output encoding and provider reference, then creates `ASSESS_DOCUMENT_IMPACT` tasks. Even an approved document remains approved after an unverified token: only verified impact or current-input/version drift invalidates it. This prevents the new behavior from treating a token as proof that a contract, valuation or disclosure changed. Real event subscription and dispatch require integration.

Source control references use the corrected deep-review index, including the Section 23 source-span correction. Assets currently reference section-scoped reviewed controls as a review basis; the references do not claim each field is a separate literal mandate or that all applicability judgments are complete.

## Lifecycle and maintenance

Period opening/close, changed evidence/facts, policy/election changes, edition changes, rejected review, contradictory evidence, failed citation and received authorisation trigger reassessment. Entity and period are required at every operation. The dependency graph connects workpapers and schedules to notes, statements and the compliance review. Downstream approvals become stale when relevant upstream revisions change. Immutable version records preserve the old content; the head changes using a local lock and compare-and-swap revision check. Duplicate work is coalesced, obsolete tasks are superseded and satisfied tasks are completed.

The lifecycle is DRAFT → IN_REVIEW → APPROVED. Changed evidence or dependencies make the current head STALE; a corrected revision supersedes the old one and requires fresh review. Missing source/evidence or required content prevents approval. A reviewer must target the exact revision/hash, differ from the owner, match the assigned reviewer name and supply complete RAG/source/index and reconciliation attestations. These are mechanical checks on supplied review records; they cannot themselves prove the reviewer or citations are genuine, or replace accounting computation. Final bundle/compliance approval also requires an explicitly empty applicable unresolved-requirement set. There is no publication or journal-posting operation.

## What is supplied and what remains open

Supplied: concrete machine/agent candidates; source-linked catalog; per-family runbooks; 68 explicit draft templates; typed event/context/revision/money schemas; a documentary RDF graph; and executable local lifecycle, outbox and observation-adapter code. Examples are explicitly synthetic/incomplete and cannot be mistaken for client statements.

Still required: production dispatcher and owned-tool authorization, source/document repositories, passage-preserving RAG, typed accounting calculations and reconciliation executors, authentic reviewer decisions, and actual connected-accounting/native acceptance proofs. The old accounting and source gaps remain open. This update establishes actionable document stewardship and reference orchestration; it does not promote the domain into the proven/full corpus or deploy changes to live engines.
