# Approve a versioned domain for corpus admission

The executable entry point is `scripts/approve-domain.sh` (Homebrew Bash 5). It implements the existing admission contract in `RealityEngine_CI/MACHINE_CONCEPT.md` §9 and the engineering contract in `RealityEngine_CI/docs/ENGINEERING_CONTRACT.md`. It does not import candidate assets, invent domain semantics, approve itself, merge PRs, or deploy a production universe.

A version identifies a reviewed machine-file inventory and its exact hashes. It is recorded by an immutable-by-policy `domain/<domain>/v<version>` approval tag, not by adding unsupported version fields to runtime machine schemas. Revisions require a new version and run. Native mappings, temporal patterns, arbitration and permission semantics are authored/reviewed inputs, not inferred from a passing test.

## States and GitHub ledger

| State | Meaning | Durable evidence |
|---|---|---|
| PLAN_ONLY_NOT_APPROVED | Read-only inventory and regeneration plan | stdout JSON |
| PREPARING_NOT_APPROVED | Development gates are running | Unique external evidence directory; commands, timestamps, exit codes, hashes |
| FAILED_NOT_APPROVED | A required step failed | Local state/events/logs; generated candidate changes remain available for inspection |
| PREPARED_PENDING_GITHUB_REVIEW | Refreshed candidate and all required gates passed | Local snapshots, source hashes, integration receipts and gate logs |
| SUBMITTED_PENDING_GITHUB_REVIEW | Candidate/evidence published for independent review | Machines ledger commit, CI evidence commit/PR when changed, Machines draft PR, explicitly NOT APPROVED candidate-evidence prerelease |
| APPROVED_MERGED | Both relevant PRs independently approved and merged; tested bytes preserved | Approval tag and GitHub release containing approval.json with reviewers, reviewed heads, PRs, merge commits, prepared-ledger hash and evidence archive hash |

The committed candidate ledger lives at `domains/approvals/<domain>/<version>/<run-uuid>.json`. Its schema forbids claiming final approval. The final approval receipt is attached to the approval release after merge, because a pre-merge commit cannot truthfully contain its own future merge hash. The two records join through the run UUID, prepared-ledger hash, source inventory and evidence archive hash.

GitHub supplies authenticated review/merge identities; a local operator name or an exit code cannot grant approval. Finalization rejects author self-approval, approvals of an old head, dismissed approvals, active changes requests, pending/failed published checks and changed tested bytes. Repository branch protection and CODEOWNERS should require the relevant technical/domain reviewers. The script requires at least one independent current-head approval even if the forge allowed an administrative merge.

Git tags and GitHub release assets are auditable, not an immutable storage service: administrators can delete tags or change assets. Keep tag protection/rulesets and verify recorded SHA-256 values. `finalize --sign-tag` uses configured Git/GPG signing; unsigned annotated tags are explicitly labeled. This script never configures identities or signing keys.

## Which machine inventories and semantic shards refresh?

| Asset | Treatment |
|---|---|
| Domain manifest | Author scope/count first; candidate status becomes accepted only after structural, parity and integration gates, then passes the accepted-candidate gate. It reaches main only through the approval PR. |
| Architecture domain registry | Authored input; must contain the domain. No automated copying of policies or arbitrary renaming of machine classes. |
| Corpus index | Regenerated from canonical machines. |
| Region-allocation inventory and arbitration registry | Regenerated for the whole shared vector; policy/output meaning still requires review. |
| Semantic-bus registry and lane contracts | Regenerated by existing canonical tools. |
| OWL ABox shards and ABox manifest | All domains regenerated with strict action vocabulary; orphan ABoxes corresponding to removed canonical machine files removed. Authored ontology/shapes/action mappings remain untouched. |
| Released semantic OWL shards | Each domain shard and the full semantic union are reasoned with ELK and HermiT; the canonical release command records a diff against the previous baseline before refreshing candidate `.owl.gz` files. These changes are reviewed in the Machines PR, not silently treated as prior approval. |
| Lane graph and decision table | Regenerated as ignored development artifacts, not force-added to Git. Exact output copies/hashes accompany the evidence archive. Source-backed reproducibility remains gated. |
| CES shards in CI | Re-recorded using the canonical recorder against real 3-of-3 engine stimulus. No fingerprints or passing verdicts are fabricated. |
| Cesgen registry in Machines | Refreshed after recordings; every planned scope must resolve as recorded. |
| Runtime machine registries | Rebuilt by canonical CI boot/load for each requested scope, queried by the machine-set and trajectory checks. The script does not edit cached runtime machine inventories by hand. |

CES scope selection deliberately includes **all known domain and configured corpus scopes**, not only scopes whose machine file hashes changed. Shared-vector contention or PE source changes can alter peer committed output without changing peer source files. This is a conservative correctness policy and can be expensive. Domain reasoning plus the full semantic union under HermiT can take tens of minutes on the development machine; execution logs retain the exact commands and durations. It also prevents a new domain from silently escaping a regression gate. Require a named regression/extension profile containing at least one actual domain representative.

## Prerequisites and candidate staging

Use sibling `RealityEngine_Machines` and `RealityEngine_CI` checkouts. Existing canonical tools discover this layout; arbitrary renamed siblings are rejected rather than silently reading a different repository. Install the repository-declared Node/Python dependencies, ROBOT and engine toolchains beforehand. Use `ROBOT_BIN` for an absolute ROBOT executable when it is not on PATH. The workflow does not install packages. Schema validation, reasoning and current-build provenance cannot be silently skipped.

Both checkouts must be on named development branches based on refreshed origin/main, with authored candidate changes committed and no unrelated tracked modifications. Commit new domains initially as experimental, with canonical machine files, manifest, architecture entry, reviewed arbitration/semantics, and regression profile as appropriate. Do not point the workflow at untracked factory JSON and call it admitted corpus.

For a new candidate branch use the normal Git workflow (fetch main; create a branch from origin/main; author and commit changes). Use a distinct CI branch for the proposed profile/recordings. The command fetches both main references before mutation and stops if a candidate needs rebasing. Unrelated untracked factory assets are left alone and never staged.

Run `plan` first from Machines:

```bash
./scripts/approve-domain.sh plan --domain health-personal --version 1.0.0
```

This is read-only: no fetch, engine reset, regeneration, status transition, commit, push or approval. It includes exact candidate hashes and all planned CES scopes. The domain must already have a canonical candidate directory and authored entries.

## Executable development runner and domain integration gate

The supplied `scripts/domain-approval/run-scope.sh` boots each requested scope through the canonical CI entry point, using cpp/lsp/scala, current-source provenance, a generated corpus manifest and a resolved instance registry URL. It runs the existing machine-set and full ISRE/OSRE trajectory checks. The approval driver then invokes CI's canonical CES recorder and refreshes the cesgen inventory.

Each domain also needs a reviewed executable integration suite. Set `DOMAIN_INTEGRATION_RUNNER` to its absolute path. This is intentionally required: one generic vector test cannot certify HealthKit, MQTT, ACP, RAG, approval or action behavior for every domain. Existing CI suites remain the authority; do not add a pass-only stub.

Integration gate interface:

```text
integration-suite /absolute/request.json /absolute/scope-output-directory
```

It receives `RE_REGISTRY_URL` and the real scope context. The request includes domain, scope, candidate source commit and the exact tested machine-file hashes. Assert applicable source→PE→RE→consumer behavior, failure/recovery and domain-specific action boundaries. Start or configure required external integrations using their authoritative CI workflows and preserve the requested scope; do not return success because an unavailable service was skipped. For scopes where a domain integration is inapplicable, the reviewed suite must execute the appropriate native/static acceptance contract and explicitly record why in the evidence rather than invent an external service result.

On success exit zero and write `integration.json` in that output directory:

```json
{
  "result": "PASS",
  "artifacts": [
    {"path": "actual-integration-test-report.json", "sha256": "<SHA-256 of actual report bytes>"}
  ]
}
```

The report must contain actual assertions, source/build/config/model provenance where relevant, observation/response receipts and limits. The suite must preserve test failures. The default runner produces the scope receipt only after real canonical parity commands and this required integration gate succeed; hashes and command logs are retained. A custom reviewed scope runner can be supplied instead, with the same request and receipt contract defined by `validate_scope_receipt` in the helper. Its content hash is pinned throughout preparation. A local receipt is evidence to review, not independently authenticated clinical truth.

## Prepare and verify

Select a **new external directory** for every attempt; failures and completed runs are not overwritten. For example, substitute your actual integration suite and evidence directory:

```bash
export DOMAIN_INTEGRATION_RUNNER=/absolute/path/to/reviewed-integration-suite
./scripts/approve-domain.sh prepare \
  --domain health-personal --version 1.0.0 \
  --regression-profile standard-deployment \
  --evidence /absolute/path/to/domain-approval-run \
  --scope-runner "$PWD/scripts/domain-approval/run-scope.sh" \
  --allow-runtime-reset
```

`--allow-runtime-reset` acknowledges that preparation stops/restarts and drives **development** engines for all planned scopes. Do not use this against a production universe. The shell driver itself contains no hidden confirmation prompt and no force-merge path.

Preparation refreshes derived views before checking them, runs schema/name/organization/fold/interconnection preflight before any resetting scope run, then performs real scope runs/recordings, runs strict corpus and explicit JSON schemas, all contract tests and domain reasoning, then rechecks the accepted candidate. IFRS Accounting additionally runs `scripts/check-ifrs-accounting-readiness.py` before live resets: the source-completeness debt and accounting findings tracked in #229 must be resolved with connected proof and independent review. The user's explicitly synthetic entity assets are allowed; they do not substitute for missing normative text or domain-wide finding closure. A connector-only pass cannot promote the domain. It rejects any authored source/config changes made during gates. The workflow uses an advisory checkout lock; other tools must still avoid modifying this checkout concurrently. On failure, inspect the retained local state/logs and candidate diff; fix/commit deliberately and start a new evidence run. There is no destructive automatic reset.

## Publish for independent review

Review local logs/artifacts before publishing: the evidence prerelease contains those files, not merely filenames. The explicit flag records the operator's review of that delivery. Preserve the original hashes; do not edit a completed run to hide a failed assertion.

```bash
./scripts/approve-domain.sh submit \
  --evidence /absolute/path/to/domain-approval-run \
  --evidence-reviewed
```

This publishes the CI shard commit and a draft PR when necessary, then the Machines pending ledger/generated-artifact commit and draft PR. It also publishes `evidence.tar.gz` in a candidate prerelease named `domain-candidate/<domain>/v<version>/<run-uuid>`, clearly labeled NOT APPROVED. The evidence archive includes commands/logs, scope requests, actual reports/receipts and instance-registry observations; its hash is committed in the ledger. No unrelated source files are staged.

A human marks PRs ready and reviews the exact heads through GitHub. Use the normal GitHub review UI or `gh pr review <url> --approve` from an independent authorized account, then the normal protected merge flow. Merge CI evidence first, then the Machines PR. The script never calls `gh pr review --approve` or `gh pr merge` itself.

Multi-repository Git publication is not atomic. Each publication step persists local progress and hashes; a network/forge failure leaves a non-approved PUBLISHING state. Inspect the recorded commits, releases and PRs before retrying or starting a new run. Do not move a version tag or call a partial publication approved. Where publication failed after a remote write, reconcile that step explicitly with the recorded run before continuing; automatic rollback would destroy audit evidence.

## Final approval receipt

After both PRs have the necessary reviews and are merged:

```bash
./scripts/approve-domain.sh finalize \
  --evidence /absolute/path/to/domain-approval-run \
  --sign-tag
```

Omit `--sign-tag` only when intentionally using an unsigned annotated tag. Finalization reads GitHub review/check/merge records, validates exact reviewed heads and tests every stored source/generated-file hash against the merge commits. It also rejects untested files added by an intervening main change, since a new peer machine can affect shared-vector behavior. A changed candidate requires a new prepared run and review. It confirms the Machines merge is on current origin/main, then creates the approval tag and release with `approval.json`. It does not retarget old tags, infer approval from a closed issue, or claim that a green hosted check replaces the local integration evidence.

Finalization network failures can leave a tag before a release exists. Keep the evidence directory; never delete/recreate an approval tag to mask a partial write. Use the recorded `approval.json` and matching merge/tag to reconcile publication. Domain rollback or withdrawal is a new reviewed change/release, never a history rewrite.

## Scope of validation for this implementation

Local tests use synthetic repositories and forge responses to exercise rejection of missing parity/integration evidence, stale/self/dismissed reviews, active changes requests, changed PR heads, tampered logs, untracked derivative coverage and failed gates. No real domain is approved, no live engines reset and no approval tag/release created merely by installing or testing this workflow. A real approval requires executing the gates and human review above.
